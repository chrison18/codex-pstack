# Interrogate: independent read-only review

Use inside explicit Poteto mode for adversarial code review, finding blind spots or challenging a concrete change. The deliverable is a synthesized verdict, not an automatic fix. Keep the checklist in conversation or authorized external scratch and inspect workspace state before/after. Do not create target files, install roles, modify configuration, commit or post review comments as a review side effect.

1. **Scope and intent.** Identify the exact files/diff and named base ref. Do not assume `main`: use the user's base or actual PR base, and retain the reviewed SHA. Gather necessary callers/types so findings have context. State the intent from the user, commit/PR and source; resolve a material ambiguity before reviewing.
2. **Resolve the entire panel before spawning.** Read the runtime contract and use `runtime.py resolve-panel PROJECT interrogate-reviewer --parent-model MODEL --parent-effort EFFORT`, with a current native catalog or supplied `--catalog`. A task-specified reviewer list uses `--selections` as a JSON array of `{model, effort}` objects. Each pair is validated using existing task > saved reviewer role > observed parent rules. Rejection blocks the whole panel before any delegate starts. No guessed Flash/Pro aliases or automatic saved preference changes.
3. **Report diversity accurately.** Without a task list the panel has two independent reviewers using the saved role or exact parent pair. This is single-model review unless the resolved model IDs differ. Show actual resolved model/effort pairs and `modelDiversity`; do not call repeated same-model attempts a multi-model review. If the user requires model diversity, choose distinct available models from the actual catalog within task authorization or report the unmet requirement. A different effort on one model is not model diversity.
4. **Independent review.** Read the [reviewer prompt](interrogate/reviewer-prompt.md), [rubric](interrogate/rubric.md) and [quality lens](interrogate/code-quality-review.md). Give the same intent, immutable diff/context and rubric to each registered `poteto-agent`, with the absolute entry/reference path, explicit read-only scope and its resolved native spawn settings. Do not share one reviewer's findings with another before its independent pass. Dispatch concurrently where supported and wait for all results. Missing role/tool support permits only a disclosed primary-only inspection, not a claim that the panel ran. A rejected explicit model cannot be evaded through fallback.
5. **Lead judgment.** Read [the judgment framework](interrogate/lead-judgment.md). Inspect every finding yourself, trace its actual execution path, merge duplicates and record which models raised it. Explain agreements and disagreements; corroboration is a signal, not proof. Bucket findings as **Act on**, **Consider**, **Noted** or **Dismissed**, with reasons. Do not auto-apply reviewers' proposals. Empty reviews are valid; do not invent findings to fill a quota.
6. **Present and audit.** State intent, reviewed refs, actual reviewers/model pairs, findings by bucket and agreement map. Include dropouts and gaps without counting them as passes. Match citations, named principles and executed-check claims to observed tools/artifacts; preserve static inference as inference. Recheck workspace state. Implementation or sending GitHub feedback needs its own authorized scope.

A role's prose is not a permission sandbox: use a read-only parent where available. Reviewers must not interpret the quality lens's restructuring suggestions as write authorization. Arena/Architect and parallel writers remain separate 3B work.
