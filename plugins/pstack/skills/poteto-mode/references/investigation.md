# Investigation

This route produces a cited answer or recommendation. It does not authorize code, configuration, repository or remote mutations.

1. Inspect relevant call paths and, for motivation questions, relevant history. Use [Interrogate](interrogate.md) for adversarial code review, [How](how.md) for runtime behavior/architecture and [Why](why.md) for motivation/history; read the applicable workflow before gathering evidence. For a mixed question, keep mechanics and historical confidence separate. Read applicable full [principle leaves](principles.md) before using their guidance. State `throughput checkpoint: n/a, read-only investigation`.
2. Keep the checklist in the conversation or an explicitly provided external scratch file. Do not create a checklist or install roles inside the investigated repository. Inspect tracked and untracked state before and after without changing it. For stronger enforcement, use a parent read-only sandbox; a role's prose is not a separate permission boundary.
3. Use the selected research/review route for scoped read-only exploration and synthesis with registered `poteto-agent` when delegation is authorized. Never install a missing role as a side effect of an investigation. Before declaring a role unavailable, follow the runtime contract's capability-evidence check: inspect directly declared native collaboration tools and their actual role schema, not only a nested `ALL_TOOLS` search. If the required role is declared and resolution succeeds, delegate as prescribed. When concrete registration/tool evidence shows it truly cannot run, gather evidence in the primary and disclose the exact limitation and that no custom role ran.
4. Follow the selected workflow's output: cited architecture/flow for How, seven-category coverage and calibrated historical evidence for Why, or a recommendation with a tradeoffs table. Cite actual files and lines or fetched sources. Distinguish observation, inference and uncertainty. Before answering, audit completion claims against the actual tool record: name a principle as applied only if its full leaf was successfully read, and name a check as executed only if its command/output was observed. Remove unsupported completion claims rather than inferring that familiar guidance or a mental simulation ran. No PR or code change follows automatically; a later requested change routes as a new Feature or Bug fix task.

How and Why are packaged workflow references under the explicit Poteto entry; read-only fallback must be disclosed. Dedicated prose and quality references are available through the workflow index, with their recorded evidence limits. Do not claim a separate native `$how` or `$why` entry loaded.

Use [Teach](skills/teach.md) for a paced explanation, [Unslop](skills/unslop.md) for prose, [Blast radius](skills/blast-radius.md) for consequences and [Poteto help](skills/poteto-help.md) for route/setup questions. The Investigation no-mutation boundary also governs those references; skip a proof script that would write to the target and disclose the scope limit. Additional routes are in the [workflow index](workflow-index.md).
