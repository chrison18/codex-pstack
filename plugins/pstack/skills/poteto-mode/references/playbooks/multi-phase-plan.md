# Multi-phase or multi-PR plan

The plan is the deliverable. Do not implement, launch owners, schedule audits, create branches/PRs or merge from a planning request. If one or two files have an obvious approach, say a separate plan is unnecessary and stop. Resolve empirical unknowns with authorized scratch prototypes; user preferences remain theirs.

Read [Technical writing](../skills/technical-writing.md) and [Unslop](../skills/unslop.md). Ground file boundaries, callers, existing commands and dependencies, using How/native read-only exploration when available. Preserve the repository's branch-per-increment rules and explicit bases. Full autonomous program execution, recurring ticks, shipping and decision-history runtime are later-phase overlays, not part of this portable plan.

Write the plan at the requested task-owned path. Include:

- Outcome, user-visible contract, scope and falsifiable completion predicate.
- How to read the checklist; who executes, who reviews/merges, and where approval stops work.
- Ordered phases/PRs with explicit dependency graph and non-overlapping ownership where parallelism is safe.
- Per unit: exact real files/symbols, requested behavior, baseline, build tasks, observable result, unit checks, live scenario(s), evidence paths, review gate and exit predicate.
- Live verification through [Control CLI](../skills/control-cli.md) or [Control UI](../skills/control-ui.md) on the actual surface. A compiled build is not a live pass. Name unavailable access and the blocked gate.
- Performance-sensitive work: named metric and units, matched trunk/head workloads, baseline before edits, interleaved samples and numeric failure rule. If trunk lacks the feature, use separate absolute budgets rather than an invalid ratio. Non-performance work explicitly states why a perf gate is inapplicable.
- Review of interaction changes with screenshots/video where applicable, plus precise source, test, CI and owner-review criteria before any separately authorized merge.
- Appendices: prototype evidence including tested refs, rejected alternatives, risks/unknowns and source links. No invented measurements, file names or completed boxes.

The inherited standing-program template's fixed ten live lanes, tick prompt, autopilot/shipping paths and strict check-plan.mjs schema belong to the unported phase 5 executor contract. This manual planning route preserves dependencies, evidence and approval gates, but does not claim compatibility with that schema or completed autonomous planning parity. Choose enough meaningful scenarios to cover the named behavior; do not pad ten duplicate checks.

Before handing back, inspect every path/command, make dependencies acyclic and ensure each unchecked box names its proof. Mark prototypes and unavailable checks truthfully. Return the plan path, dependency order, review-gated set, actual prototype findings and validation limits; then wait for an explicit implementation request.
