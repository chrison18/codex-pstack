# Applicable principles

These 24 full leaves are adapted from the inherited pstack principles. They are reference material inside the explicitly activated Poteto workflow, not additional native skill entries. Select only the leaves relevant to the current decision and read those leaves in full before applying them. Name a principle only after reading its full leaf and only when it changed a concrete decision. Reading this index does not complete that step. The user's scope, host permissions and repository Git rules still govern execution.

| Decision | Read in full |
| --- | --- |
| Apply when two or more fixes that share one premise have failed the same gate. Write the premise down and test it directly before you write another fix that assumes it. | [Attack the Premise](principles/principle-attack-the-premise.md) |
| Apply when wiring validation, error handling, or framework adapters. Concentrate guards at system boundaries (CLI, config, network, external APIs); trust internal types and keep business logic in pure functions. | [Boundary Discipline](principles/principle-boundary-discipline.md) |
| Apply to any non-trivial work, not just bulk work: edits, migrations, analyses, checks. Build the tool that does it or proves it (codemod, script, generator, or a skill your subagents follow) instead of working by hand. The tool is the artifact a reviewer can rerun. | [Build the Lever](principles/principle-build-the-lever.md) |
| Apply when you catch yourself writing the same instruction a second time, or notice a recurring correction. Encode the rule as a lint, metadata flag, runtime check, or script instead of more text. | [Encode Lessons in Structure](principles/principle-encode-lessons-in-structure.md) |
| Apply when facing a novel UI interaction or architectural decision with no precedent in the codebase. Build 2-3 competing prototypes and compare side by side before committing. | [Exhaust the Design Space](principles/principle-exhaust-the-design-space.md) |
| Apply when product, UX, or feature-scope tradeoffs come up. Choose user delight over implementation convenience; ship fewer polished features over more rough ones. | [Experience First](principles/principle-experience-first.md) |
| Apply before you trust, report, or act on a number you measured: a speedup, a regression, a throughput, a latency, or an eval result. Find what limits it, and rule out that it measured something other than the work you think. | [Explain the Number](principles/principle-explain-the-number.md) |
| Apply when debugging. Trace each symptom back to the first place the system went wrong and fix it there. A guard is a fix only when the state it handles is legitimate. | [Fix Root Causes](principles/principle-fix-root-causes.md) |
| Apply before writing logic: choosing core types and data structures, sequencing scaffold-vs-feature work, asking what concurrent actors share. Get the data structures right so downstream code becomes obvious. | [Foundational Thinking](principles/principle-foundational-thinking.md) |
| Apply when context is filling up: large outputs, long files, repeated reads, fan-out planning. Route bulk to subagents; keep summaries in the main thread, not raw payloads. | [Guard the Context Window](principles/principle-guard-the-context-window.md) |
| Apply when refactoring, evaluating diff size, or tempted to add abstractions, layers, or signal threading. Bias toward deletion and the smallest change that solves the problem. | [Laziness Protocol](principles/principle-laziness-protocol.md) |
| Apply when designing commands, lifecycle steps, or processing loops that run amid crashes, restarts, and retries. Converge to the same end state regardless of partial prior runs. | [Make Operations Idempotent](principles/principle-make-operations-idempotent.md) |
| Apply when introducing a new internal API while old callers still exist. Migrate callers and delete the old API in the same wave instead of preserving compatibility layers. | [Migrate Callers Then Delete Legacy APIs](principles/principle-migrate-callers-then-delete-legacy-apis.md) |
| Apply when reviewing or shaping code that's hard to trace. Count layers between question and answer, and hidden state in the reader's head; collapse one-caller wrappers and shrink mutable scope. | [Minimize Reader Load](principles/principle-minimize-reader-load.md) |
| Apply when writing stateful logic, or when code branches a lot or repeats a shape assumption across files. | [Model the Domain](principles/principle-model-the-domain.md) |
| Apply when tempted to ask 'should I do X?' on reversible work. | [Never Block on the Human](principles/principle-never-block-on-the-human.md) |
| Apply during planned rewrites and migrations with explicit phase boundaries. Converge on the target architecture; don't preserve smooth intermediate states with throwaway compatibility code. | [Outcome-Oriented Execution](principles/principle-outcome-oriented-execution.md) |
| Apply after completing a task, before declaring done. Verify against the real artifact (run the feature, read the actual value, inspect the diff), not a proxy, self-report, or 'it compiles.' | [Prove It Works](principles/principle-prove-it-works.md) |
| Apply when integrating a new requirement into an existing design. | [Redesign From First Principles](principles/principle-redesign-from-first-principles.md) |
| Apply when concurrent actors might write to the same file, branch, key, or state object. Eliminate the sharing first; serialize structurally only when one shared writer is a real invariant. | [Separate Before Serializing Shared State](principles/principle-separate-before-serializing-shared-state.md) |
| Apply to multi-step work (sweeps, migrations, runs of similar edits) and to how you stack commits and PRs. Break work into small units that each end in a verifiable state, check each before the next, and order delivery so the sequence proves itself to a reviewer. | [Sequence work into verifiable units](principles/principle-sequence-verifiable-units.md) |
| Apply when sequencing an addition, refactor, or rewrite. Remove dead code, redundant validators, and stub references first, then build on the simpler base. | [Subtract Before You Add](principles/principle-subtract-before-you-add.md) |
| Apply when you write, change, or keep a test. Assert what the code's users can observe, so that the test fails when that behavior breaks and keeps passing when only the internals change. | [Test Behavior, Not Implementation](principles/principle-test-behavior-not-implementation.md) |
| Apply when designing types, reviewing a function signature, or writing code in any statically-typed language. Make illegal states unrepresentable, brand semantic primitives, parse external data at boundaries, exhaust variants, derive from authoritative schemas. | [Type System Discipline](principles/principle-type-system-discipline.md) |
