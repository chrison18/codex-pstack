## User outcomes, ordering and decision boundary

Convenient **Orca Chat startup** is directly blocked by unobserved UI submission/discovery/loading, not by missing advanced performance/formal tests. **One maintained pstack workflow across participants** has substantial CLI/native evidence and package-local fixes; it still needs intended-client loading and honest route-specific capability claims. Do not promise that every existing global agent automatically adopts pstack, or simplify Lingentic policy based only on this audit.

**Recovery and continued execution** are not implemented by this acceptance work. The original plan assigns A10/A11 and durable goal/requirements/completed/pending/evidence state to phase 4, and A12 wake/cancel/restart/duplicate/completion to phase 5. Those phases remain blocked by full 3B2 closure and merge under the current dependency graph. Higher-end design pools, live multi-category research, formal tooling, Eval, browser parity and production recovery breadth are optional for many individual user tasks, but their retained migration gates cannot be demoted by this inventory.

Recommended next executable bounded task, following the current outcome document: **one Architect convergence regression**, predeclared to accept a correctly disclosed incomplete stop, with inspectable equivalent artifacts and unchanged authority. It addresses a newly introduced completion safeguard, not a fresh full-workflow certification campaign. Do not require both replacement and stop permutations, different models, or another successful repair in the same task. Then return to the original remaining design code-worktree/actual-failure queue and the shared gate matrix, rather than growing a Scrap-specific test program. Before an additional native run, review fixture provability and ensure it tests package judgment rather than a prompt commanding the expected answer.

In parallel read-only planning, identify an eligible live Why case and an actually supported Chat input surface. Repeating the same Slack dispatch, protected write or Chromium/focus failure without changed conditions adds no evidence. The concrete prior failures above are blockers to those exact probes, not proof that every future client/version or supported method is unavailable.

If those environments remain unavailable, the coordinator may propose either (a) retain strict order and wait for a supported surface/eligible case, or (b) a narrowly documented support boundary or further increment split with an explicit plan revision and owner decision, preserving blocked claims and publication history. Option (b) is **not approved here** and does not authorize phase 4, claim full 3B, or merge PR #6. No silent scope reduction, global configuration change or UI/security bypass is an acceptable substitute.
