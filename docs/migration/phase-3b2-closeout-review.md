**PROPOSAL ONLY — minimal dependency/support-boundary revision for owner consideration:** split current 3B2 into a reviewed core acceptance increment and a separately tracked advanced-capability acceptance increment. The core increment must still prove actual Orca Chat startup/positive/follow-up/ordinary controls and supported installation, retained core routes/delegate instruction loading, ownership/base safety and current CI/review; no weakening of these user-visible requirements. Explicitly retain advanced Why/Eval/runner-fault/native-visual claims as unsupported or pending in the latter increment, with their current evidence and prerequisites. Change only phase 4's prerequisite from full 3B2 to the merged core increment; keep phase 5 dependent on completed/merged phase 4, and final phase 6 acceptance accountable for all retained claims and owner outcomes. A10/A11/A12 recovery, cancellation, idempotency and continued-execution tests remain intact. This proposal does not make advanced capabilities mandatory for every ordinary task or declare them implemented.

In plain terms, the decision is whether to **wait for every current capability prerequisite before building memory/continuation**, or **first prove convenient Orca startup and the supported everyday workflow, then build durable progress while advanced capabilities stay visibly pending**. Neither option allows claiming Chat startup or autonomous continuation before its own tests pass. The smallest owner decision is approval or rejection of that explicit split; if approved, the migration plan and PR boundaries must be revised and reviewed before dependent work or merge. No such approval has been received, no plan file is changed, and PR #6 remains draft.
