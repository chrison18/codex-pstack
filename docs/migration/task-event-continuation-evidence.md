# One-shot task-event continuation

2026-11-02 candidate on merged PR #9 base `e6b0bc15cce125c1ab13f45eb115c4914189d518`. Scope: an authorized external caller delivers one explicit event to a named bounded task; the adapter starts a fresh Orca Chat and retains the existing continuation contract. No event source, scheduled job, same-Chat sender or unattended service is installed. Package version remains `0.2.0-alpha.1`; source pin and all 87 inventory classifications are unchanged.

## Design and supported host boundary

Version-matched Orca **1.4.245** CLI guidance and command registry document `agent launch --agent codex --surface chat --worktree path:… --prompt … --json` and known-operation `--retry-launch` replay. No documented structured same-Chat send/settlement command was established; terminal PTY control is not substituted. Advertised capabilities alone were not treated as callable APIs. No old failed terminal probe was repeated, automation installed or private store searched broadly.

The caller supplies observed prior-writer settlement and an explicit exclusive-owner assertion. Exact-project search maps the owned Chat to a capture containing actual turn completion; artifacts corroborate its checkpoint. That historical completion alone cannot prove current inactivity, so unknown liveness/ownership blocks delivery. This is cooperative ownership, not host-enforced exclusion.

`task_event.py` persists canonical workspace/task/owner/event binding, token, resolved executable/argv and launch intent before calling the host, without holding the task lock across launch. Structured/journaled acceptance is not settlement. Duplicate delivery never launches again; a different event cannot bypass an unsettled one. A crash/lost/malformed reply retains intent/unknown and holds, even when no effect can be proven. Known-operation replay is documented but not automatically reconciled by this adapter. Receiver claim and continuation mutation guards reject copied/mismatched bindings and require the event token. Cancellation and completion are terminal; cancellation cannot preempt a running host launch, and a late receiver must check terminal state before task effects.
